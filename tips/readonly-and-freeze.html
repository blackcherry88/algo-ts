01 One mental model to rule them all

Every immutability feature in TypeScript lives in exactly one of two worlds. Ninety percent of confusion comes from mixing them up.

🧊 Typeland — compile time

A pinky promise checked by tsc, then erased. Zero bytes ship. Anyone with any, a cast, or plain JS walks right past it.

Members

readonly props · readonly T[] · Readonly<T> · as const · ReadonlyMap/Set · const type params

🔒 Runtime City — actual JS

A real lock on the object. Survives into production, throws TypeError in strict mode, and stops every caller regardless of types.

Members

Object.freeze · Object.seal · Object.defineProperty · const bindings · #private, closures

The one-liner to memorize: readonly and as const protect you from yourself and your teammates. Object.freeze protects you from the program. They are orthogonal — good API design often uses both.
Third axis, easy to forget: const is neither of those two things for objects. const freezes the binding (which box the name points at), never the contents of the box. const xs = [1]; xs.push(2) is perfectly legal in both worlds.

03 readonly properties

A property modifier. It blocks assignment to that property, nothing more. Not the object, not what's inside it. 

interface User {
  readonly id: string;      // set once, never reassigned
  name: string;             // freely editable
  readonly tags: string[];  // the *slot* is locked, the array is not!
}

const u: User = { id: "u_1", name: "Tao", tags: ["admin"] };

u.name = "Hu";              // ✅ fine
u.id = "u_2";               // ❌ TS2540: Cannot assign to 'id', it is read-only
u.tags = [];                // ❌ TS2540 — replacing the array
u.tags.push("root");        // ✅✅ ALLOWED. Shocking, but correct: you did not
                            //    assign to `tags`, you mutated the array it holds.
Trap #1, the big one. readonly tags: string[] means "you can't swap the array out", not "the array is immutable". Want both? Say readonly tags: readonly string[]. The modifier and the element type are two separate decisions.

In classes

class Point {
  readonly x: number;
  constructor(x: number) {
    this.x = x;           // ✅ constructors get one free write
  }
  move(dx: number) {
    this.x += dx;         // ❌ TS2540 everywhere else
  }
}

// Shorthand: parameter properties
class Vec {
  constructor(
    public readonly x: number,
    public readonly y: number,
  ) {}
}

Readonly<T> — the mapped-type version

type Readonly<T> = { readonly [K in keyof T]: T[K] };   // lib.es5.d.ts

type Frozen = Readonly<{ a: number; nested: { b: number } }>;
// { readonly a: number; readonly nested: { b: number } }
//                       ^^^^^^^^ ONE LEVEL ONLY. `nested.b` is wide open.

declare const f: Frozen;
f.nested = { b: 1 };   // ❌ blocked
f.nested.b = 2;        // ✅ allowed — shallow!

Need it deep? There is no built-in. Write it once and reuse (mind the array and function cases): 

type DeepReadonly<T> =
  T extends (...args: never[]) => unknown ? T
  : T extends readonly (infer E)[] ? readonly DeepReadonly<E>[]
  : T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;

The inverse is -readonly, which strips modifiers — this is exactly how the built-in Mutable-style helpers work: 

type Mutable<T> = { -readonly [K in keyof T]: T[K] };

04 Readonly arrays, tuples, Map & Set 

const a: readonly number[] = [1, 2, 3];      // preferred syntax
const b: ReadonlyArray<number> = [1, 2, 3];  // identical type
const c: readonly [string, number] = ["x", 1];   // readonly tuple

a[0] = 9;        // ❌ TS2542: Index signature in type 'readonly number[]'
                 //    only permits reading
a.push(4);       // ❌ TS2339: Property 'push' does not exist
a.sort();        // ❌ mutating methods are simply absent from the type
const d = a.concat([4]);   // ✅ non-mutating methods stay → number[]
const e = [...a, 4];       // ✅ spread to get a fresh mutable copy

ReadonlyArray<T> is not a subtype of Array<T> — it is the supertype. Mutating methods were removed, so assignability runs one way only: 

let mut: number[] = [1];
let ro: readonly number[] = mut;   // ✅ widening: dropping abilities is safe
mut = ro;                          // ❌ TS4104: The type 'readonly number[]' is
                                   //    'readonly' and cannot be assigned to the
                                   //    mutable type 'number[]'
Free API upgrade. Type every function parameter you don't mutate as readonly T[]. Callers with a plain T[] still pass, you gain a compiler-enforced "I won't touch your array", and readers learn the contract without opening the body. Same story for ReadonlyMap<K,V> and ReadonlySet<T>. 
// Before: does this sort in place?? Have to read the body.
function median(xs: number[]): number { ... }

// After: the signature answers the question.
function median(xs: readonly number[]): number {
  const sorted = [...xs].sort((p, q) => p - q);   // forced to copy. Good.
  const m = sorted.length >> 1;
  return sorted.length % 2 ? sorted[m] : (sorted[m - 1] + sorted[m]) / 2;
}

05 as const — the const assertion

Two effects at once, which is why it feels magic:

Effect Without as const With as const
1. No literal widening { dir: "up" } → { dir: string } { dir: "up" } → { dir: "up" }
2. Deep readonly [1, 2] → number[] [1, 2] → readonly [1, 2] 
const move = { dir: "up", by: 2 };
// { dir: string; by: number }   ← widened, mutable

const moveC = { dir: "up", by: 2 } as const;
// { readonly dir: "up"; readonly by: 2 }   ← literal + readonly, recursively

const nested = { a: { b: [1, 2] } } as const;
// { readonly a: { readonly b: readonly [1, 2] } }   ← DEEP, unlike Readonly<T>
Deep in Typeland, nothing at runtime. as const is an assertion — it compiles to nothing at all. moveC is a bog-standard mutable JS object. (moveC as any).dir = "down" succeeds.

Killer app #1 — literal types survive into function calls

declare function rotate(dir: "up" | "down"): void;

const cfg = { dir: "up" };
rotate(cfg.dir);      // ❌ TS2345: Argument of type 'string' is not assignable
                      //    to parameter of type '"up" | "down"'

const cfgC = { dir: "up" } as const;
rotate(cfgC.dir);     // ✅ type is "up"

Killer app #2 — the enum replacement

export const Status = {
  Idle: "idle",
  Loading: "loading",
  Done: "done",
} as const;

export type Status = (typeof Status)[keyof typeof Status];
// "idle" | "loading" | "done"   ← derived, never hand-maintained

Read the type line right-to-left: typeof Status is the object's type, keyof gives "Idle"|"Loading"|"Done", indexing with it gives the union of values. Without as const you'd get string and the whole trick collapses.

Beats enum because it is plain JS (no emitted runtime object, works under isolatedModules and type-stripping runtimes like Bun/Node's native TS), and the values are real strings you can log, JSON.stringify, and compare to API payloads.

Killer app #3 — tuple inference

const pair = ["x", 1];              // (string | number)[]  😖
const pairC = ["x", 1] as const;    // readonly ["x", 1]     😍

// Infamous React idiom — hooks must return tuples, not unions:
function useToggle(init = false) {
  const [on, setOn] = useState(init);
  return [on, () => setOn(v => !v)] as const;   // readonly [boolean, () => void]
}

as const satisfies T — order matters

type Route = { path: string; method: "GET" | "POST" };

const routes = {
  home: { path: "/", method: "GET" },
  send: { path: "/send", method: "POST" },
} as const satisfies Record<string, Route>;

routes.home.method;   // "GET" — the *narrow* type is kept
//                       An annotation `: Record<string, Route>` would have
//                       widened it to '"GET" | "POST"' and lost the keys.
// And typos are still caught: method: "PUT" → error.
as const satisfies X = "lock it narrow, then prove it fits X". Best of both: validation without widening. Always in that order.

const type parameters (TS 5.0+)

Push as const behaviour into the callee so callers don't have to type it: 

function pick<T extends readonly string[]>(keys: T): T { return keys; }
const p1 = pick(["a", "b"]);         // string[]  😖 caller must write `as const`

function pickC<const T extends readonly string[]>(keys: T): T { return keys; }
const p2 = pickC(["a", "b"]);        // readonly ["a", "b"]  😍 automatic

06 Object.freeze — the only real lock

The single tool on this page with runtime teeth. It does four things to an object:

  • every existing property → writable: false
  • every existing property → configurable: false (so no delete, no redefining)
  • the object → extensible: false (no new properties)
  • prototype → locked (no Object.setPrototypeOf)
"use strict";                 // ESM & class bodies are always strict
const o = Object.freeze({ n: 1, inner: { m: 2 } });

o.n = 2;            // 💥 TypeError: Cannot assign to read only property 'n'
o.extra = 3;        // 💥 TypeError: Cannot add property extra, not extensible
delete o.n;         // 💥 TypeError: Cannot delete property 'n'
o.inner.m = 99;     // ✅ NO ERROR — freeze is SHALLOW
Object.isFrozen(o);         // true
Object.isFrozen(o.inner);   // false  ← the whole story in one line
Sloppy mode silently no-ops. In non-strict code o.n = 2 fails without throwing — the write just evaporates, which is the nastiest debugging session of your year. Modules and class bodies are strict automatically; a classic <script> tag is not.

TypeScript knows about freeze

const f = Object.freeze({ n: 1 });   // inferred: Readonly<{ n: number }>
f.n = 2;                             // ❌ caught at compile time too!

const fa = Object.freeze([1, 2, 3]); // readonly number[]
fa.push(4);                          // ❌ TS + 💥 runtime. Belt and braces.

So Object.freeze gives you both worlds in one call — that's why it is the right choice for exported constants and shared defaults. The cost: a real runtime call, and V8 can deoptimize hot paths that write to frozen objects. Freeze module-level config, not million-element arrays in a loop.

Relatives

Call Add props Delete props Change existing
Object.preventExtensions ❌ ✅ ✅
Object.seal ❌ ❌ ✅
Object.freeze ❌ ❌ ❌

Deep freeze, correctly

function deepFreeze<T>(o: T): DeepReadonly<T> {
  for (const v of Object.values(o as object)) {
    // guard against cycles AND against re-walking already-frozen subtrees
    if (v && typeof v === "object" && !Object.isFrozen(v)) deepFreeze(v);
  }
  return Object.freeze(o) as DeepReadonly<T>;
}

The isFrozen check is not an optimization — it is the cycle guard. Freeze before recursing (or check first, as above) or a.b = a stack-overflows.

08 The Trap Gallery

Every one of these has shipped a bug. Learn them as a set.

Trap 1 · readonly is not checked on assignability 

interface RO { readonly n: number }
interface MUT { n: number }

declare const ro: RO;
const m: MUT = ro;   // ✅ NO ERROR. TypeScript ignores readonly modifiers
m.n = 99;            // ✅ ...and now you've mutated `ro` through an alias.

This is a deliberate, documented unsoundness (arrays are the exception — they are checked). Never treat readonly props as a security boundary across an API. If it must hold, Object.freeze it or hand out a copy.

Trap 2 · const ≠ immutable

const xs = [1, 2];
xs.push(3);        // ✅ fine, xs is [1,2,3]
xs = [];           // ❌ TS2588 / TypeError: Assignment to constant variable

const is about the name. as const is about the type. Object.freeze is about the value. Three different nouns.

Trap 3 · Readonly<T> and freeze are shallow, as const is deep 

const A: Readonly<{ i: { n: number } }> = { i: { n: 1 } };
A.i.n = 2;                                   // ✅ allowed (shallow)

const B = { i: { n: 1 } } as const;
B.i.n = 2;                                   // ❌ blocked (deep)

const C = Object.freeze({ i: { n: 1 } });
C.i.n = 2;                                   // ✅ allowed, TS *and* runtime

Ranked by depth: as const (deep types) > Readonly<T> / Object.freeze (one level) > const (zero levels).

Trap 4 · The mutation escape hatches

const o: Readonly<{ n: number }> = { n: 1 };

(o as any).n = 2;                 // ✅ compiles — cast defeats readonly
(o as { n: number }).n = 2;       // ✅ compiles
Object.assign(o, { n: 2 });       // ✅ compiles! Object.assign's signature
                                  //    doesn't respect readonly at all
o["n" as keyof typeof o] = 2;     // creative, still compiles in some configs

Every one of those is blocked at runtime if and only if you also called Object.freeze. Types advise; freeze enforces.

Trap 5 · Copies lose their frozenness

const frozen = Object.freeze({ n: 1 });
const copy = { ...frozen };          // NOT frozen
const clone = structuredClone(frozen); // NOT frozen
JSON.parse(JSON.stringify(frozen));    // NOT frozen

// Idiomatic "update" — copy, change, re-freeze:
const next = Object.freeze({ ...frozen, n: 2 });

That's the good news, actually: it's how immutable updates work. Spread produces a fresh unlocked object you can shape before locking again.

Trap 6 · Frozen arrays throw on the fun methods 

const a = Object.freeze([1, 2, 3]);
a.push(4);       // 💥 TypeError: Cannot add property 3, object is not extensible
a.sort();        // 💥 in-place mutation
a.length = 0;    // 💥 length is a property too
[...a].sort();   // ✅ copy first, always

Trap 7 · Odd corners of freeze

Object.freeze(42);                  // returns 42 — primitives are already immutable
Object.isFrozen(42);                // true (spec quirk, not a bug)
Object.freeze({});                  // no own props → vacuously frozen forever

const m = Object.freeze(new Map()); // ⚠️ internal slots are NOT protected
m.set("k", "v");                    // ✅ works! freeze only guards properties.
                                    //    Use ReadonlyMap types + don't hand out the Map.

09 Which one do I reach for?

I want to… Use Why
Say "this function won't touch your array" readonly T[] param Free, callers unaffected, self-documenting
Set a field once, in the constructor readonly prop Idiomatic, zero cost
Keep string literals narrow for a union as const Prevents widening to string
Replace an enum as const object + typeof indexing Plain JS, no emitted runtime, type-strip friendly
Return a tuple from a function/hook as const Tuple instead of union array
Validate a literal table without widening it as const satisfies T Narrow types + checked shape
Export a shared config that must never change Object.freeze (or deepFreeze) Only option with runtime enforcement
Make a whole existing type read-only Readonly<T> / DeepReadonly<T> Mapped type, no value-level change
Guarantee immutability across a trust boundary deepFreeze + return copies Types are erased and castable; locks are not
Cheap structural sharing on big state copy-on-write (spread) or a library (Immer) Deep-freezing large trees costs real time
Default policy that ages well: readonly everywhere in types (params, props, fields) because it's free; as const on every literal table and returned tuple; Object.freeze only on exported constants and shared mutable defaults, where a stray write would be a real incident.

The 20-second recap. const locks the name. readonly locks a property slot, at compile time, shallowly, and is ignored when checking object assignability. as const locks a literal's type, deeply, at compile time, and vanishes at runtime. Object.freeze locks the object, for real, shallowly, and TypeScript rewards you with Readonly<T>. If a rule must survive a cast, it has to be a freeze.
